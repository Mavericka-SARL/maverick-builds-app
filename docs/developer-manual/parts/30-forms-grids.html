Records

Sidebar: Developer › Records

A table holds the records people save: purchase requests, expense claims, headcount changes, deals. This screen defines each table's fields. Records are entered, searched and reviewed through a Records widget on a dashboard; posting record values into planning cells is configured under Integrations › Records.

Status and workflows

  • No status field, no status. A table without a status field gives its records no status: a record counts in the metrics its integrations post into as soon as it is saved, and saving it fires the table's submitted trigger.
  • A status field means approval. With one, a new record starts as a draft. Its creator may move it between draft and submitted; an administrator may set any status. An integration posts a record only in the statuses it names (approved by default). Records saved before the field was added keep no status and keep counting.
  • The workflow moves it. A workflow whose subject is the table (Single saved record in a table or Selected records in a table, under the workflow's Properties) and which has an approval step drives the status of the record its run is about — the record a form_submit trigger names: submitted while the run is open, approved or rejected by its last decision, a draft again if the run is cancelled. The record is posted again as it moves, as the approver. A test run moves nothing.
  • Adding or removing the field re-posts the table. Removing a table's status field makes every record count, so its records are posted again; the Save message says so.

Rules and behaviour

  • Tables are per revision. The list and the create action use the selected revision. Editing never moves a table to another revision.
  • Same name overwrites. Creating a table whose technical name already exists in the revision silently replaces that table's label and fields. Pick a new name for a new table.
  • Delete cascades. Deleting a table removes every dashboard widget that shows it and every record ever saved in it.
  • Records live on dashboards. Users and business admins work on records only in a dashboard Records widget: search, filters and a sort by any column (they cover every record the person may see, not one page), the pencil to edit a record, the status list, delete, Export (of what the widget shows) and Import (CSV and XLSX), and, for an administrator, Sync to grid — each offered only when the server allows it to that person. + New record is shown only when the widget's developer added it (the widget's Show the + New record button). The developer screen has no record controls.
  • Values are checked on the server. A dimension field takes a leaf member the person can see — a hidden member is answered like an unknown code; a metric field chosen by name takes an input metric the person can see; required fields must be filled; numbers, dates and true/false are checked. An import checks every row the same way and imports nothing if one fails.
  • Access rules decide where a record may post. A save that would post into a cell the person may not write — a member or metric that is read-only for them, a workflow-locked cell — is refused with a message naming the member or metric (a hidden one is not named). Where a field posts on save, the member picker leaves out the members the person may only read. A draft that does not post yet may name such a member: an approver who may write there approves it.
  • What people see follows their access rules. A record naming a member or a metric hidden from a person — through a dimension field, a fixed metric field, or a metric field chosen by name — is left out of their list, search, totals and export.
  • Posting to cells is a separate object. A table mapping (Integrations › Records) decides which field feeds which input metric, at which dimension members, for which record statuses. Metric and Dimension field types exist so the mapping has something to read.
  • Where tables appear. Users and business admins open a table through a dashboard Records widget. A table that is on no dashboard is not reachable by them: place every table people fill in on a dashboard their business role is granted. The chat connector and the AI Developer read a table's records too (read-only; query_records).

Grids

Sidebar: Developer › Grids

A grid is a selection of metrics and dimensions that is shown as one table. It holds no data of its own; the data lives in the model. The same metric can only sit in one grid, so grids partition the model's metrics into the tables users will edit.

Rules and behaviour

  • One grid per metric. Ticking a metric that already belongs to another grid is refused by the server and the box stays unticked after refresh. Untick it in the other grid first. Dimensions can be shared freely.
  • Same revision. Metrics and grid must be in the selected revision; a mismatch is refused.
  • Deleting a grid deletes its widgets. Every dashboard widget that showed the grid disappears; the dashboards themselves stay.
  • Rename and tags. The pencil renames a grid and edits its tags; widgets that show the grid keep showing it. Tags travel with the grid: a new revision and a model export copy them.
  • Where the table comes from. A grid becomes visible to users through a dashboard Grid widget (Dashboards chapter). The widget decides which dimension is rows, columns or a selector; the grid only decides the ingredients.
  • Level display. Choosing Leaves only hides parent members from the axis; totals for parents are still computed and appear where the widget shows them.
