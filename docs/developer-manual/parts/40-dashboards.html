Dashboards

Sidebar: Developer › Dashboards

A dashboard is the page a user opens. It is a free-form canvas of widgets: grids to plan in, charts and KPIs to read, records to enter and review, buttons that start workflows or integrations, text and pictures, and an import box. Dashboards are organised in folders and tagged, and are granted to business roles on the Users screen.

The canvas: Design and Preview

The toolbar shows Dashboards (back), the dashboard name, the widget count, the Design / Preview switch and, in Design mode, the widget palette: Grid, Chart, Records, Board, Metric KPI, Trigger, Integration, Text, Image, Import, Workflow status.

Text takes a small Markdown subset — # headings, **bold**, *italic*, `code`, bullet and numbered lists, > quotes, --- rules and links — [label](https://example.com) to another site, or [label](/docs/formulas-manual/manual.html) to a page of this deployment such as the manuals it ships with. Both open in a new tab, so the console stays where it was. A link can also open another dashboard in place: [label](dashboard:Dashboard name) for one of the same model, [label](dashboard:Model name/Dashboard name) for one of another model, and [label](dashboard:Model name/) for another model's first dashboard. Link to a dashboard… under the text box writes one for you: pick a model and a dashboard, then Insert link. Such a link names the model and the dashboard rather than pointing at them, so it keeps working through a revision copy, an export and an import; rename the target and the link says it cannot find it. It follows the reader's own access: a model they cannot open or a dashboard their roles hide is reported, never shown. A link can open a page of the sidebar too, by the names it shows: [label](page:Workflow Inbox), or with its group [label](page:Developer › Dimensions) when two groups have a page of that name (Roles, Dashboards, Models; without a group the first group in the sidebar wins). It opens the page as a click in the sidebar would; a reader whose roles do not give them that page is told so instead. In Design and Preview dashboard and page links are inert; they work under User › Dashboards. Plain text that uses none of it is shown as typed. Image takes a PNG, JPEG, SVG, WebP or GIF of up to 512 KB, chosen with a file picker; the picture is stored with the dashboard, so it travels with a revision copy, an export and an import, and it takes alternative text for screen readers and a Fit of "show all of it" or "fill the box". Together they are what an explanatory page is built from — the tour a new workspace starts with is written in exactly these widgets.

  • Design is for placing and configuring widgets. Nothing is live.
  • Preview renders the dashboard exactly as a user gets it, against the revision you are designing, and includes property edits you have not saved yet. Values typed into a grid in Preview are real writes.

Adding a widget

Click a palette chip; the Configure & place panel opens. Pick the source and click Add widget. The widget is placed at the first free spot at its default size, unsaved until Save.

WidgetSource and what it shows
GridGrid: one grid of the revision. Renders the editable planning table (below).
ChartGrid (source), then the chart editor (below). Add widget stays disabled until the chart configuration is complete.
RecordsTable: people search, filter, sort, edit, import and export that table's records here. Show the + New record button (off by default) also lets them add records here.

Dragging a card to another column, or choosing one in the card's list, changes that field; the server checks it as any save. The rest is set in Widget Properties.

TriggerTrigger: an automation rule with trigger type manual that is enabled. If none exists the panel says so. Renders a button that starts the rule's workflow.
IntegrationIntegration: a REST API integration. Renders a button that runs it.

It names no person and shows no comment, so it belongs on a page everyone reads, such as a guide.

Moving, sizing, selecting

  • Drag the widget header to move; drag the right edge, bottom edge or corner to resize. Everything snaps to 20 px.
  • Keyboard: arrow keys nudge by 20 px, Shift+arrow by 100 px, Alt+arrow resizes, Escape deselects.
  • Widgets may not overlap. A colliding drop snaps back and the other widget shows "Overlaps another widget" while you drag.
  • Minimum sizes: grid 600×300, chart 360×240, records 360×300, KPI 220×120, import 320×280, text 240×100, buttons 40×20.
  • The × on a card asks Delete widget?; the source object (grid, table, rule) is not deleted.

Each card in Design mode shows a Selectors strip: which dimensions this widget lets the user choose, whether they are synced, own, pinned or total, and, when another widget owns the shared selector, "dim → Owner". A dimension on the dashboard's selector bar reads "dim (bar)".

Selector bar

Without a bar, synced widgets that share a dimension show one selector for it, on whichever widget appears first, which is not always the widget it matters most to. When several widgets share a dimension such as a scenario or a period, give the dashboard a selector bar: Selector bar in the Design toolbar, + Add dimension, then pick the dimension and the member it opens on (or first member), and Save selector bar. It is saved on its own, not with the layout.

The bar sits at the top of the dashboard, one selector per dimension, and stays in view while the page scrolls. Every grid and chart follows it and shows no selector of its own for those dimensions, also one with Context sync off, which keeps only its other selectors to itself. A KPI follows it when set to Follow dashboard selectors or Follow the selector bar. A tile showing a company total should use Follow the selector bar: Follow dashboard selectors also takes one member of each of the metric's other dimensions. A KPI pinned to a member or showing the whole-model total keeps that. A person who cannot see the opening member gets the dimension's first member they can see. The bar follows the dashboard into a new revision and into a model export; renaming a member code updates it. Up to 8 dimensions; a dimension appears once. The AI Developer sets it with selector_bar on create_dashboard and update_dashboard.

Duplicate / DeleteDuplicate copies the widget with its current, even unsaved, settings to a free spot. Both wait for Save like every other change.
Save is explicit. Every change on the canvas — adding, duplicating and deleting a widget, moving and resizing it, and its properties — raises an unsaved-changes bar with Save and Cancel. Save writes them all (new widgets created, deleted ones removed, the rest updated); Cancel drops them all; leaving the page while dirty asks first. If a save fails part-way, what was written stays written and the bar keeps the rest with the reason. An incomplete chart configuration is never saved; the last complete one stays. The selector bar is saved by its own editor.

What users get: the planning grid

  • Editing. Input metrics are inputs; a value is committed on Enter or when leaving the cell. Non-numeric text is discarded. "Saving…" and "Save failed: …" appear while writing.
  • Read-only cells. Calculated metrics, aggregated parent members, members or metrics the user's access rules mark read-only, and grids that mirror another grid are not editable.
  • Selectors. One selector per context dimension the widget owns, plus a Metric selector when Metrics is in the context zone. Selectors are searchable trees; with synced widgets, a choice applies to all of them.
  • Click to select. Clicking a row or column label sets that member in every synced widget. The legend says so when sync is available.
  • Totals. A hierarchical column axis adds a read-only Total column per parent group; a flat row axis with more than one row adds a bold Total footer row.
  • Hierarchies render fully expanded, indented per level, parents in bold. There is no collapse control.
  • Grid actions (⋯): Export the grid's values as a file, and Pivot data, a panel where the user drags Metrics and dimensions between Rows, Columns and Context selectors.
  • Hidden members never reach the browser: the server strips members and metrics the user may not see and flags read-only ones. If a widget is pinned to a member the viewer cannot see, the first visible member is used instead.

Making a dashboard reachable

A user sees a dashboard only when one of their business roles has been granted it. Grants are managed on the Users screen (Users chapter). Until then the dashboard exists only for developers.
